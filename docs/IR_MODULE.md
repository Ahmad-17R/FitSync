# Information Retrieval module

FitSync's retrieval component, built for the IR assignment (presentation
12–13 October 2026). It follows the presentation order the assignment asks for:
problem, requirement, models, implementation, queries, results, comparison,
conclusion. Full per-query output is in [`IR_RESULTS.md`](IR_RESULTS.md),
generated by `python -m ir.evaluate --markdown`.

---

## 1. FYP problem

FitSync coaches yoga in real time. Detecting a mistake is not the same as
teaching the fix, though. When the coach says *"Straighten and root down
through your standing leg"*, the user should be able to see the whole guide for
that pose: the steps, the common mistakes, what to be careful of. When users plan a
session they ask in their own words: *"something gentle for my lower back"*.

## 2. Retrieval requirement

| | |
|---|---|
| **What is retrieved** | Pose guides |
| **Document** | One guide per pose (30, in `server/ir/data/yoga_corpus.json`), split into fields: name + Sanskrit, tags (level, category, body parts), overview, steps, benefits, cautions, mistakes + corrections |
| **Query, from the user** | Free text typed on `/search`, e.g. `gentle stretch lower back` |
| **Query, from the system** | A correction the live coach gave, sent from the session summary's *Read the guide* link, e.g. `Tree Pose Straighten and root down through your standing leg` |
| **Result** | Guides ranked by relevance, each with a matching snippet and a per-term score breakdown; or, for structured queries, the exact regions of text that match |

The 8 poses the live coach tracks use the server's exact correction strings in
their guides. A test checks this, and another checks that all 25 corrections
the coach can give retrieve their own pose's guide first.

## 3. IR models used

| Topic from class | Where | What it does here |
|---|---|---|
| **Boolean model** | `ir/boolean.py` | AND / OR / NOT over posting lists, with precedence, parentheses and `field:word` |
| **Binary Independence Model** | `ir/ranking.py` `bim_search` | Sum of `log((N−df+0.5)/(df+0.5))` for each query word present; optional pseudo-relevance feedback |
| **BM25** | `ir/ranking.py` `bm25_search` | BIM's rarity × saturating term frequency × document-length normalisation (k1 = 1.2, b = 0.75) |
| **BM25F** (extension) | `ir/ranking.py` `bm25f_search` | BM25 with per-field weights: name 3, mistakes 1.5, cautions 0.6 … |
| **Non-overlapped lists** | `ir/structured.py` | Three flat region lists (section, fault, sentence); `cautions CONTAINING knee`, `sentence CONTAINING arms WITHIN steps` |
| **Overlapped lists** | `ir/structured.py` | `knee ... ankle` builds spans that may overlap each other; shortest-substring reduction |
| Inverted + positional index, stemming, stopwords | `ir/index.py`, `ir/text.py` | Shared by all of the above, ported from the course engine |
| Evaluation: P@k, R@k, MAP, MRR | `ir/evaluate.py` | 5 judged queries |

## 4. Implementation

```
user / live coach ──► GET /api/search?q=…&model=…      (FastAPI, server/api/search_routes.py)
                          │
                          ▼
                 text.py  tokenize → stopwords (+ "pose", "yoga") → Porter2 stem
                          │
                          ▼
                 index.py inverted index · per-field index · positional stream + regions
                          │
          ┌───────────────┼──────────────────┬───────────────────┐
          ▼               ▼                  ▼                   ▼
     boolean.py      ranking.py         ranking.py         structured.py
     set algebra     BIM (+feedback)    BM25 / BM25F       region lists
          │               │                  │                   │
          └───────────────┴─────────┬────────┴───────────────────┘
                                    ▼
          ranked guides + snippet + per-term evidence  ──►  /search page (web/)
```

**Endpoints:** `/api/search`, `/api/search/compare`, `/api/search/structured`,
`/api/search/benchmarks`, `/api/search/docs/{slug}`.

**UI:** `/search` has four tabs: Search (pick a model, *Why this rank?*
shows the numbers), Compare models, Structured, Evaluation.

**Tests:** `server/tests/test_ir.py`, 37 tests. They cover:
- each model on a tiny corpus you can check by hand
- BM25 saturation and length normalisation, and BIM ignoring term frequency
- regions within one list never overlapping
- the overlapped-span counts
- every API endpoint
- that the coach links land on the right guide

## 6. Results

| Model | P@3 | P@5 | R@5 | MAP | MRR |
|---|---|---|---|---|---|
| Boolean * | 0.733 | 0.600 | 0.850 | 0.800 | 0.900 |
| BIM | 0.333 | 0.320 | 0.510 | 0.616 | 0.535 |
| BIM + feedback | 0.333 | 0.280 | 0.470 | 0.598 | 0.524 |
| **BM25** | 0.733 | 0.600 | 0.850 | **0.904** | **1.000** |
| **BM25F** | 0.733 | 0.600 | 0.850 | **0.904** | **1.000** |

\* Boolean returns an unordered set. Its ranked numbers use document-id order
and are not meaningful; per query, its set precision/recall is 1.0/1.0 on Q1, Q3
and Q4, 0.5/0.5 on Q2, and 1.0/0.75 on Q5.

## 7. Comparison: why each model behaves the way it does

**Boolean vs BM25 on Q2.** `beginner AND balance NOT floor` drops **Tree Pose**,
the best answer, because its overview says it "roots into the floor". Boolean
cannot tell an incidental word from the topic of a guide. It also cannot rank:
on Q3 it finds exactly the right five guides, but in an order that means
nothing. BM25 puts Tree first.

**BIM vs BM25 on Q3.** BIM ranks *Mountain Pose* first for "gentle stretch lower
back". Why:
- "back" is in 22 of 30 guides, "lower" in 23 and "stretch" in 16. With
  `log((N−df+0.5)/(df+0.5))`, words in more than half the collection get
  **negative** weights, counted as evidence *against* relevance.
- So a guide matching all four words is penalised three times.
- Mountain matches only "gently" (from "lift your kneecaps gently") and scores
  higher than all of them.

BM25's idf, `log(1 + …)`, never goes negative, and it adds term frequency and
length normalisation. It ranks the five relevant guides 1–5.

**BIM ignores term frequency (Q4, Q5).** On Q5 BIM gives Tree, Warrior I and
Upward Salute an identical score: each contains "arm" and "overhead", and
nothing else counts. BM25 breaks the tie by length. Upward Salute is a short
guide *about* raising the arms, so its matches count for more.

**BIM + feedback made things worse.** Pseudo-relevance feedback assumes the top
3 are relevant. When they are not (Q2, Q3), it re-weights terms towards the
wrong guides and reinforces the error, which is known as query drift.

**BM25 vs BM25F.** Same metrics here, but BM25F separates the right answer more
clearly. On Q1 Tree scores 8.66 vs 6.89, because "tree" is in its **name**,
weighted 3×. With a larger corpus that margin is what keeps a guide *about* a
topic above one that merely *mentions* it.

**Non-overlapped vs overlapped lists.**
- `cautions CONTAINING knee` returns the exact caution sentence, not just
  "this guide matched somewhere", which is what a coach needs to show.
- `knee ... ankle` returns 15 spans with 2 overlapping pairs. A non-overlapped
  list cannot represent that answer.
- `WITHIN fault` narrows it to the 3 corrections about stacking the knee over
  the ankle.

**What no lexical model can do.** Chair Pose is relevant to Q5, but its guide
says "reach your arms up alongside your ears", never "overhead". Every model
here matches words, so none of them finds it. This is the vocabulary-mismatch
problem. The next step is query expansion with a yoga thesaurus (English ↔
Sanskrit, *overhead* ↔ *arms up*).

## 8. Conclusion

BM25 is the right default for FitSync's guide search, and BM25F, which uses the
guide structure, is what the app ships with. Boolean stays useful for hard
filters. BIM is a good teaching baseline, and its failures show what each part
of BM25 adds. Structured search turns retrieval from "which guide" into "which
sentence of which guide", which is the form the coach actually needs.

## Feynman explanations

Each one follows the same four steps: what goes in, what happens inside, what
comes out, and why that result came first.

**Boolean.** A librarian who only answers yes or no.
- *In:* `standing AND leg AND bent AND tree`.
- *Inside:* each word is a pile of guides that contain it, and AND keeps only
  the guides in every pile.
- *Out:* one guide, Tree.
- *Why first:* nothing is ever "first". Everything that passes is equally good.

**BIM.** A detective who trusts rare clues.
- *In:* `standing leg bent tree`.
- *Inside:* "tree" appears in 1 guide out of 30, so finding it is a strong clue
  (+2.98). "leg" appears in 20, so finding it says almost nothing; it even
  counts slightly against (−0.67).
- *Out:* Tree 3.10, Chair 0.79.
- *Why first:* Tree is the only guide holding the rare clue. The detective
  doesn't care how many times a clue appears, only whether it's there.

**BM25.** The same detective, plus two common-sense rules.
- *In:* the same query.
- *Inside:* rule one, a word said 9 times counts more than once, but not 9
  times more (it saturates). Rule two, a long guide mentions everything, so its
  matches are shrunk. Tree's guide is 115 words against an average of 80, so
  its length norm is 1.32.
- *Out:* Tree 6.89 (tree 3.71 + standing 1.55 + bent 0.84 + leg 0.77), then
  Mountain 2.99.
- *Why first:* Tree is the only guide naming the pose, *and* it talks about the
  standing leg nine times.

**Non-overlapped lists.** A book with chapters, paragraphs and sentences, each
listed separately.
- *In:* `cautions CONTAINING knee`.
- *Inside:* look only through the "cautions" chapter of each guide, and keep the
  ones containing "knee".
- *Out:* the sentences themselves.
- *Why first:* guides with more matching regions come first, then the tighter
  match.

**Overlapped lists.** Highlighting with a marker that can start anywhere.
- *In:* `knee ... ankle`.
- *Inside:* from every "knee", highlight to every "ankle" that follows within 12
  words.
- *Out:* "knee knee … ankle" gives two highlights, one inside the other. The
  shortest is marked, because it is the tightest evidence.
